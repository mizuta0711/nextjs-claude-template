# テンプレート最新化レビュー（2026-08-12）

- **対象**: `nextjs-claude-template`（Claude Code ハーネス設定一式）
- **観点**: 最新の Claude Code 仕様（2026-08 時点の公式ドキュメント）との差分・陳腐化・改善余地
- **調査方法**: リポジトリ全ファイル確認 + Claude Code 公式ドキュメント（hooks / settings / skills / sub-agents / memory / plugins / sandboxing）の実地照合
- **前提**: Next.js は 16.3 が最新安定版（16 系が現行メジャー）。**スタック前提そのものは陳腐化していない**

## 0. 総評

構成の骨格（規模判定 S/M/L → 2段階設計 → レビュー → 設計書同期）は完成度が高く、そのまま維持してよい。
一方で **Claude Code 側がこの数か月で機能を大きく増やしており、テンプレートがその恩恵をほぼ受けられていない**。特に以下の3点が大きい。

1. **`.claude/rules/` + `paths:` によるルールの遅延ロード** が未使用 → CLAUDE.md が 252 行（公式推奨は 200 行以下）に肥大し、DB 3点同期のような「特定ファイルを触るときだけ効けばよいルール」が常時ロードで薄まっている
2. **フックの `if` フィールドが公式仕様化された** → コミット `7bd8ca1` で「公式仕様ではない」としてスクリプト内判定へ移行した判断が、現在は逆に非効率（Bash 呼び出しのたびに node プロセスが3つ起動する）
3. **スキル / サブエージェントのフロントマター機能がほぼ未使用**（`allowed-tools` / `context: fork` / 動的コンテキスト注入 / `tools` 制限 / `effort` / `skills` プリロード）

加えて、**動かない・実態とズレている箇所が4件**ある（§1）。

## 2. 🔴 いま壊れている / 実態とズレている箇所

### 2.1 ✅ `update-docs` の `HEAD~${0:-1}` は動かない

> **対応済（`4ea1985`）**: 下記の修正案どおり `arguments: [depth]` + `argument-hint` を導入し、本文から `$0` を排除した。

[.claude/skills/update-docs/SKILL.md:13](../../.claude/skills/update-docs/SKILL.md#L13)

```bash
git diff --name-only HEAD~${0:-1}
```

現在の Claude Code は SKILL.md 本文で `$0` を **`$ARGUMENTS[0]` の短縮形として置換する**。引数ありなら `${1:-1}` のような意図しない文字列になり、引数なしなら未置換のまま bash に渡り、bash の `$0`（シェル名）が入って `HEAD~bash` になる。どちらも失敗する。

**修正案**（フロントマターで名前付き引数を宣言する形が最も明快）:

```yaml
---
name: update-docs
description: 実装変更に基づいて設計書の更新が必要な箇所を特定し、更新を実行する。コミット前に実行する。
argument-hint: "[遡るコミット数（省略時は1）]"
arguments: [depth]
---
```

```bash
# $depth は未指定時に空文字へ展開されるため、Step 1 の指示文で既定値を明記する
git diff --name-only HEAD~$depth
```

もしくはシンプルに `git diff --name-only HEAD~1` に固定し、「複数コミットを遡る場合は `$ARGUMENTS` の数値を使う」と地の文で指示する。

### 2.2 ✅ `done/SKILL.md` にフロントマターがない

> **対応済（`4ea1985`）**: `name` / `description` を追加。当初案の `disable-model-invocation: true` は下記の理由で撤回した。

[.claude/skills/done/SKILL.md](../../.claude/skills/done/SKILL.md) は `# 作業完了報告` から始まっており、YAML フロントマターがない。
`description` が本文1段落目からのフォールバックになるため、Claude の自動起動判断が不安定になる。

```yaml
---
name: done
description: 作業完了時に、決められたテーブル形式で完了報告を出力する。S/M/Lフローの最終ステップ。
---
```

> ⚠️ `disable-model-invocation: true` は**付けてはいけない**。`done` は CLAUDE.md の S/M/L フローで
> Claude 自身が最終ステップとして実行するスキルであり、これを付けると Claude から起動できなくなり
> フローが成立しなくなる（当初この案を検討したが、フロー定義と矛盾するため撤回した）。

### 2.3 ✅ `complete-feature` の `user_invocable` はフィールド名が誤り

> **対応済（`4ea1985`）**: 不正キーを行ごと削除し、`disable-model-invocation: true` に置き換えた。

[.claude/skills/complete-feature/SKILL.md:4](../../.claude/skills/complete-feature/SKILL.md#L4)

## 3. settings.json

### 3.1 ✅ 権限設定が共有されていない

> **対応済（`a4be874`）**: `.claude/settings.json` に allow 17 / ask 5 / deny 12 を新設。
> 下記の提案から3点を変更した。
> - `git reset --hard` は **deny ではなく ask** に。CLAUDE.md「バグ修正の原則」がロールバック手段として推奨しており、deny だと自己矛盾するため
> - `.env` の deny は一括 `Read(./.env*)` を避け、Next.js の命名規則に沿って個別指定。`.env.example` を読めるまま残すため
> - `git push` は **ask ではなく allow** に。push のタイミングは CLAUDE.md「push のタイミング」で行動ルールとして既に縛られており、
>   毎回の確認プロンプトは冗長なため。強制 push（`--force` / `-f`）は deny のまま残すので、危険な操作は引き続きブロックされる
>
> `.claude/settings.local.json` は変更していない（gitignore 対象のマシン固有設定）。deny はどのレイヤーの allow よりも優先されるため、local に広い allow が残っていても deny は有効。

現在、`permissions` は **`.claude/settings.local.json` にしか存在せず、これは `.gitignore` 済み**。
つまり「Use this template」で複製した先には権限設定が一切引き継がれない。テンプレートとしては致命的な欠落。

さらに、その local 側の内容にも問題がある:

- `allow` に `Bash(rm:*)` `Bash(curl:*)` `Bash(bash:*)` `Agent` が入っており、実質ほぼ無制限
- `deny` の `Bash(rm -rf /:*)` `Bash(rm -rf C::*)` は**ほぼ機能しない**。パーミッションルールは前方一致パターンなので、`rm -rf /usr` は止まるが `rm -rf ./src` や `cd / && rm -rf *` は素通りする
- CLAUDE.md に「シークレットはコードに書かない」と書いてあるのに、`.env` の**読み取り**を deny していない

**共有すべき方針を `.claude/settings.json`（コミット対象）へ移す** 案:

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run build)",
      "Bash(npm run lint)",
      "Bash(npm run dev)",
      "Bash(git status)", "Bash(git diff:*)", "Bash(git log:*)", "Bash(git add:*)",
      "Bash(npx tsc --noEmit)",
      "Bash(npx prisma generate)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(rm -rf *)",
      "Bash(git push --force*)",
      "Bash(git reset --hard*)",
      "Bash(npx prisma migrate reset*)"
    ],
    "ask": [
      "Bash(git reset:*)",
      "Bash(npx prisma migrate:*)"
    ]
  }
}
```

`.claude/settings.local.json` には「そのマシン固有の緩和」だけを残す。

### 3.2 ✅ `CLAUDE_CODE_AUTO_COMPACT_WINDOW` は設定キーへ移行

> **対応済（`a4be874`）**: `env` ブロックを削除し `autoCompactEnabled: true` + `autoCompactWindow: 500000` に移行。
> `effortLevel` は `high` のまま据え置いた（`xhigh` / `max` はコスト増のため、必要な工程だけスキル側の `effort` で引き上げる方針）。

```json
// 現在（env 経由）
{ "env": { "CLAUDE_CODE_AUTO_COMPACT_WINDOW": "500000" } }

// 現行仕様（トップレベル設定キー。100k〜1M）
```

あわせて `effortLevel` は現在 `low` / `medium` / `high` / `xhigh` / `max` が選べる。設計レビューのような判断の重い工程は、スキル側の `effort` フロントマターで局所的に引き上げるのが効率的（§5.6）。

## 4. フック

### 4.1 ✅ `if` フィールドは公式仕様になった

> **対応済**: コメントの訂正が `4ea1985`、`settings.json` への `if` 付与が `a4be874`。
> 実際に指定した値は `Bash(npx prisma migrate:*)` / `Bash(git commit:*)`（下記例の `Bash(git commit *)` 形式ではなく、
> 引数なしの `git commit` も確実に拾えるパーミッションプレフィックス構文を採用）。
> スクリプト内の正規表現判定は二重防御として保持した。

3つのフックスクリプト全てに以下のコメントがある:

> Claude Code の `if` フィールドは公式仕様ではないため、コマンド判定は本スクリプト内で stdin の JSON を読んで行う。

**これは現在は誤り。** `if` はパーミッションルール構文で公式サポートされており、`PreToolUse` / `PostToolUse` / `PostToolUseFailure` / `PermissionRequest` / `PermissionDenied` で評価される。Bash パターンではサブコマンド、`$()`・バッククォート内、先頭の `VAR=value` 除去まで見てくれる。

現状は **Bash ツールを呼ぶたびに node プロセスが 3 つ起動して即 exit している**（探索中の `ls` 一発でも 3 プロセス）。`if` に戻せばこのオーバーヘッドが消える。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(npx prisma migrate *)",
            "command": "node .claude/hooks/pre-migrate-backup.js",
            "timeout": 60,
            "statusMessage": "DB バックアップ中..."
          },
          {
            "type": "command",
            "if": "Bash(git commit *)",
            "command": "node .claude/hooks/pre-commit-type-check.js",
            "timeout": 120,
            "statusMessage": "型チェック中..."
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(git commit *)",
            "command": "node .claude/hooks/post-commit-doc-check.js",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

スクリプト側の正規表現判定は**残しておいてよい**（二重防御 + 単体テストしやすさ）。ただしコメント文言は修正が必要。

なお `timeout` は**秒単位**で正しく書けている（60 / 120 / 10 秒）。

### 4.2 🔶 ブロック手段が強すぎる

> **一部対応（`a4be874`）**: `pre-commit-type-check.js` を `permissionDecision: "deny"` へ変更。
> `pre-migrate-backup.js` は **意図的に `continue: false` のまま**とし、その理由をスクリプト冒頭のコメントに明記した
> （バックアップなしで破壊的な DB 操作へ進ませないため、人間の判断を必ず挟む）。この非対称は仕様。

`pre-commit-type-check.js` / `pre-migrate-backup.js` はエラー時に以下を返している:

```js
{ continue: false, stopReason: "Type check failed. ..." }
```

`continue: false` は **Claude を完全に停止させる**フィールド。型エラーは「Claude に直させたい」事象なので、ツール呼び出しだけを拒否して理由を返す形が正しい:

```js
console.log(JSON.stringify({
  hookSpecificOutput: {
    hookEventName: "PreToolUse",
    permissionDecision: "deny",
    permissionDecisionReason: "型エラーがあります。修正してから再度コミットしてください:\n" + out
  }
}));
```

これで Claude は理由を受け取って自己修復ループに入れる。DB バックアップ失敗のように**人間の判断が要る**ケースだけ `continue: false` を残すのが妥当。

### 4.3 🟠 使っていないフックイベント

現在 30 近いイベントがあるが、使っているのは PreToolUse / PostToolUse の 2 つだけ。このテンプレートのワークフローに直結するもの:

| イベント | 用途 |
|----------|------|
| `SessionStart`（matcher: `startup\|resume`） | `additionalContext` で「現在のブランチ / 未プッシュコミット数 / `docs/features/` の進行中設計書」を自動注入。毎回の状況説明が不要になる |
| `PostToolUse`（matcher: `Edit\|Write`, if: `Edit(src/**/*.{ts,tsx})`） | 変更ファイルだけ `eslint --fix` + `tsc` の増分チェック。`/build-check` まで待たずに気づける |
| `Stop` | 未コミットの変更が残っていたら通知 |
| `SubagentStop`（matcher: `coding-specialist`） | 「サブエージェントの結果は必ずメインで差分確認」という CLAUDE.md のルールを機械的に強制できる |
| `PreCompact` | 進行中の機能設計書パス・規模判定結果を退避（コンパクトで失われがちな情報） |
| `FileChanged`（matcher: `schema.prisma`） | DB 3点同期ルールの発火点 |
| `InstructionsLoaded` | `.claude/rules/` 導入後、どのルールがいつ読まれたかのデバッグ用 |

### 4.4 🟡 型チェックフックのコスト

`pre-commit-type-check.js` は毎コミットで**プロジェクト全体の `npx tsc --noEmit`** を回す。テンプレ段階では空だが、実プロジェクトに育つと1コミットあたり数十秒。フック timeout 120 秒に対しスクリプト内 timeout 60 秒という二重設定も、超過時の挙動が分かりにくい。

- `tsc --noEmit --incremental` + `tsBuildInfoFile` でキャッシュを効かせる
- または §4.3 の `PostToolUse(Edit)` 増分チェックに寄せ、コミット時は `git diff --cached` 対象に絞る

## 5. スキル

### 5.1 🟠 `/code-review` がバンドルスキルと名前衝突している

Claude Code には**バンドルの `/code-review` が存在する**。プロジェクト定義が優先されるため現状は project 版が動くが、その副作用として **`/code-review ultra`（ブランチ全体のマルチエージェント・クラウドレビュー）が呼べなくなっている**。

対応の選択肢:

1. プロジェクト側を `/review-impl` などにリネームし、バンドル `/code-review` を温存する（推奨）
2. 衝突を許容し、CLAUDE.md に「ultra レビューは使えない」と明記する

あわせて、既存フローに組み込む価値のあるバンドルスキルがある:

| バンドルスキル | 組み込み先 |
|----------------|-----------|
| `/security-review` | CLAUDE.md「セキュリティの原則」の実行手段。push 前フローに追加できる |
| `/simplify` | `/code-review` の後段。品質面のクリーンアップ専用 |
| `/run` `/verify` | `/browser-test` の前段。アプリを実際に起動して変更が効いているか確認 |

### 5.2 ✅ `allowed-tools` 未使用 → 毎回の権限プロンプト

> **対応済（`a4be874`）**: `build-check` / `code-review` / `update-docs` / `sync-check` / `pre-push-check` の5件に付与。
> 各スキルの本文に実際に書かれているコマンドのみを列挙し、推測での追加はしていない。

`build-check` は毎回 `npm run build` / `npm run lint` の許可を求める。スキル起動ターンに限って事前承認できる:

```yaml
---
name: build-check
description: ビルド・lint・型チェックを一括実行し、結果を報告する。
allowed-tools: "Bash(npm run build), Bash(npm run lint), Bash(npx tsc --noEmit)"
---
```

同様に `pre-push-check` / `sync-check` には `Bash(git log:*)` `Bash(git diff:*)` `Grep` を、`update-docs` には `Bash(npx tsx tools/scripts/generate-table-docs.ts)` を付けられる。

### 5.3 🟠 動的コンテキスト注入が未使用

現在は「Step 1: 以下のコマンドを実行してください」と**指示している**が、スキル読み込み時点で**実行結果を本文に埋め込める**。1ターン節約でき、実行忘れも起きない。

```markdown
## Step 1: レビュー対象

未コミットの変更:

!`git diff --name-only`

直近コミットの変更:

!`git diff --name-only HEAD~1 HEAD`
```

`code-review` / `update-docs` / `pre-push-check` / `browser-test` の Step 1 は全てこの形にできる。

> ⚠️ ネイティブ Windows で Git Bash がない環境では `` !`...` `` が失敗する。その場合はフロントマターに `shell: powershell` を指定する。WSL / Dev Container 前提なら不要。

### 5.4 🟡 `context: fork` でコンテキスト分離

`sync-check` は全量照合で大量の grep 結果を読む。`pre-push-check` も同様。これらは**結論だけメインに返せばよい**ので、フォークして専用サブエージェントで走らせるとメインのコンテキストを汚さない。

```yaml
---
name: sync-check
description: 設計書と実装の網羅的な突き合わせチェック。
context: fork
agent: documentation-manager
background: false
---
```

### 5.5 🟡 `browser-test-checklist.md` の置き場所

[.claude/browser-test-checklist.md](../../.claude/browser-test-checklist.md) は `.claude/` 直下にあり、**どの仕組みからも自動ロードされない**。読ませるには誰かが明示的に Read する必要がある。

- 案A: `.claude/skills/browser-test/checklist.md` へ移し、SKILL.md から `${CLAUDE_SKILL_DIR}/checklist.md` として参照
- 案B: `browser-tester` エージェントの `skills:` プリロード対象にする

### 5.6 🟡 その他の未使用フロントマター

| フィールド | 適用先 |
|-----------|--------|
| `disable-model-invocation: true` | `done` / `complete-feature` / `pre-push-check`（Claude の勝手な起動を防ぐ） |
| `arguments: [mode]` | `design-review` の `feature\|tech` を `$mode` で受ける |
| `effort: high` | `design-review` / `code-review`（判断の重い工程だけ引き上げ） |
| `model` | スキル単位のモデル上書き（`update-docs` は `haiku` でも足りる可能性） |
| `paths` | 特定ファイル編集時のみ自動ロード |
| `hooks` | スキルのライフサイクルに閉じたフック定義 |

## 6. CLAUDE.md とドキュメント構造

### 6.1 🟠 CLAUDE.md 252行 → `.claude/rules/` へ分割

公式の推奨は **200行以下**（長いほどコンテキストを食い、遵守率が下がる）。現在 252 行 / 14KB。

重要なのは行数そのものより、**「特定のファイルを触るときだけ効けばよいルール」が常時ロードで薄まっている**こと。`.claude/rules/` に `paths:` 付きで置けば、該当ファイルを読んだ瞬間に確実にロードされる。

```
.claude/rules/
├── typescript.md      # paths: ["src/**/*.{ts,tsx}"]        ← any 禁止、型定義ルール
├── react.md           # paths: ["src/features/**/*.tsx", "src/components/**"]  ← memo/useCallback、UI実装ルール
├── api.md             # paths: ["src/app/api/**"]           ← NextRequest/NextResponse、Service 層経由
├── prisma.md          # paths: ["prisma/schema.prisma", "tools/export-to-sql.ts"]  ← DB 3点同期・バックアップ必須
└── scripts.md         # paths: ["tools/**"]                 ← スクリプト整理ルール
```

ルート CLAUDE.md に残すのは、**毎セッション必要な全体方針だけ**:

- 対話は日本語
- サブエージェントのモデル指定方針
- 規模判定（S/M/L）と開発フロー
- 作業完了時の報告フォーマット
- push のタイミング / 作業の進め方
- ドキュメント構成の役割分離（参照ルール）

特に **DB 3点同期ルールは `prisma.md` に移すと効果が跳ね上がる**。「スキーマを触った瞬間に必ず読まれる」保証が付くため。

> 注意: `.claude/rules/` の `paths:` ルールは**コンパクト後に自動再注入されない**（該当ファイルを次に読んだ時に再ロード）。長時間セッションでスキーマ変更する場合の挙動として認識しておくとよい。

### 6.2 🟡 CLAUDE.md 内の HTML コメント

メンテナ向けのメモは `<!-- ... -->` で書くとコンテキストに載らない（ブロックレベルの HTML コメントは注入前に除去される）。改訂メモ等に使える。

### 6.3 🟡 オートメモリとの関係整理

オートメモリ（`~/.claude/projects/<project>/memory/`）は既定で有効。このテンプレートは「設計書に実態を書く」思想なので、**オートメモリと `docs/設計書/` で二重管理になりうる**。テンプレートとしてどちらを正とするか方針を CLAUDE.md に一文書いておくとよい（例: 「実態の記録は `docs/設計書/` を正とする。オートメモリはユーザー個人の作業習慣のみ」）。

### 6.4 🟡 `/doctor` の CLAUDE.md トリム提案

`/doctor` はチェックイン済み CLAUDE.md に対して「コードから導出できる内容（ディレクトリ構成・依存一覧）を削り、落とし穴・根拠・慣習だけ残す」トリム案を出す。§6.1 の分割前に一度かけると判断材料になる。

## 7. サブエージェント

### 7.1 🔶 `tools` / `disallowedTools` 未指定

> **一部対応（`a4be874`）**: `product-advisor` のみ読み取り専用化。
> 適用時に各エージェント本文を精査した結果、他4件は書き込みが本務のため制限不可と判明した（下表）。
> `browser-tester` には代わりに `mcpServers: ["playwright"]` を付与し、Playwright を必要とするエージェントに限定した。

5 つのエージェント全てが `name` / `description` / `color` / `model` のみで、**全ツール（Write / Edit / Bash 含む）を継承している**。

特に問題なのは:

- **`product-advisor`** — 本文に「実装は行わず、戦略・企画レベルの助言に専念する」と書いてあるが、**実際には編集可能**。プロンプトによる自制に頼っている
- **`code-reviewer`** — 設計レビュー（`/design-review`）で呼ぶときはレビューだけしてほしいが、設計書を書き換えられる

```yaml
# product-advisor.md
---
name: product-advisor
description: ...
model: sonnet
color: purple
tools: Read, Grep, Glob, WebSearch, WebFetch
---
```

一方、以下は**制限してはいけない**（実際に適用してみて判明した）:

| エージェント | 制限できない理由 |
|-------------|-----------------|
| `code-reviewer` | `/code-review` がレビュー結果を `docs/reviews/` に書き出し、重要度「重要」の指摘を自動修正する仕様。`Write` / `Edit` 必須 |
| `browser-tester` | エビデンスフォルダへの `report.md` 保存が必須仕様（「保存せずに終了しない」と明記）。`Write` 必須 |
| `documentation-manager` | 設計書の更新が本務 |
| `coding-specialist` | 実装が本務 |

つまり **§7.1 で実際に効くのは `product-advisor` のみ**。ただしこれは「レビュー観点として無意味」という意味ではなく、
各エージェントの本務が書き込みを含むかを1件ずつ確認する必要がある、ということ。

### 7.2 🟠 有効な新フロントマター

| フィールド | 適用案 |
|-----------|--------|
| `skills` | `browser-tester` にチェックリストを、`coding-specialist` に開発ドキュメントをプリロード（毎回 Read させる往復が消える） |
| `mcpServers: ["playwright"]` | `browser-tester` だけに Playwright を載せる。他エージェントのコンテキスト節約になる |
| `effort` | `code-reviewer`（設計レビュー時）は `high`、`documentation-manager` は `low` |
| `maxTurns` | 暴走防止の上限（特に `coding-specialist`） |
| `permissionMode` | `documentation-manager` は `acceptEdits`（設計書更新は自動承認）等 |
| `isolation: worktree` | 大規模リファクタや並列実装で衝突を避ける |
| `memory` | サブエージェント個別のオートメモリ |

### 7.3 🟡 `model: "sonnet"` 明示の冗長さ

`design-review` / `browser-test` の Agent 呼び出し例は `Agent(subagent_type: "code-reviewer", model: "sonnet", ...)` と書いているが、モデルはエージェント定義側の frontmatter で既に `sonnet`。呼び出し側の明示は不要（残しておいても害はないが、二重管理になる）。

なお **v2.1.198 以降、サブエージェントは既定でバックグラウンド実行**になった。「呼び出して結果を待つ」前提でスキルを書いている箇所は、必要なら `background: false` を明示する。

## 8. MCP / 外部ツール

### 8.1 `.mcp.json` のバージョン固定

```json
{ "args": ["@playwright/mcp@latest"] }
```

`@latest` はテンプレートとしては再現性が落ちる（更新で挙動が変わってもテンプレ側で検知できない）。バージョンをピン留めし、定期的に上げる運用を推奨。

### 8.2 TypeScript LSP プラグインの導入

公式マーケットプレイスに TypeScript の LSP プラグインがある。Next.js + TS(strict) プロジェクトでは、**型情報ベースの参照解決・定義ジャンプが grep より正確**になるため、`sync-check` や `code-review` の精度に直結する。

```
/plugin marketplace add anthropics/claude-plugins-official
/plugin install typescript@claude-plugins-official
```

### 8.3 `enabledMcpjsonServers`

`.mcp.json` は初回に承認ダイアログが出る。テンプレートとして `"enabledMcpjsonServers": ["playwright"]` を `.claude/settings.json` に置いておくと、複製先で即使える。

## 10. 🟡 サンドボックスと Dev Container の関係

`docs/guide/サンドボックス環境移行ガイド.md` と `.devcontainer/` で WSL + Dev Container 構成は整備済み。これに加えて、Claude Code には**ビルトインの Bash サンドボックス**がある（`/sandbox` で設定、`settings.json` の `sandbox` キー）。

- 対応: **macOS / Linux / WSL2**。ネイティブ Windows は非対応
- 効果: コマンドごとの承認ではなく、**触れるファイル・到達できるドメインを宣言**して OS に強制させる → 権限プロンプトが大幅に減る
- Dev Container の代替ではなく**併用**するもの（コンテナ内でさらに Bash を隔離する）

すでに WSL ネイティブへ移行済みなので、そのまま恩恵を受けられる。`.devcontainer/devcontainer.json` の `postCreateCommand` に Linux 用の依存パッケージ導入を足しておくと、コンテナ起動直後からサンドボックスが有効になる。
