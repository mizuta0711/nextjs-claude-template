## 1. 概要

### 背景

[20260812_テンプレート最新化レビュー.md](../../reviews/20260812_テンプレート最新化レビュー.md) で、Claude Code の現行仕様とテンプレートの差分を19件洗い出した。
うち Phase 1（`4ea1985`）と Phase 2（`a4be874` / `3225ec1`）で 11 件を対応済み（✅8 / 🔶3）。

残る8件のうち、**設定値の変更では済まず、テンプレートの構造そのものを変える必要があるもの**を本 Phase で扱う。
Phase 1・2 が「壊れているものを直す」「設定を現行仕様に合わせる」だったのに対し、本 Phase は「**構成を作り替える**」。

### 目的

| # | 解決したい課題 | 現状 |
|---|---------------|------|
| 1 | CLAUDE.md 252行の常時ロードで、個別ルールの遵守率が下がっている | 全ルールが毎セッション読まれ、DB 3点同期のような重要ルールが薄まる |
| 2 | フロー上の重要ルールが「Claude が覚えていること」に依存している | 差分確認・型エラー検知・状況把握が人間の指示待ち |
| 3 | バンドルスキル `/code-review` および `/code-review ultra` が名前衝突で使えない | プロジェクト定義が優先され、本体の差分レビュー／クラウドレビューに到達できない |
| 4 | `browser-test-checklist.md` がどこからも自動ロードされない | 明示的に Read しない限り参照されない |

> **課題1の根拠について**: Stage 1 レビューで「本テンプレート固有の失敗事例がなく、根拠が公式の200行推奨という一般論のみ」との指摘を受けた。
> これは妥当な指摘である。
>
> **実施結果**: `/doctor` は Claude Code の CLI 組み込みコマンドであり Claude 側から起動できないため、
> 代わりに着手前に**セクション別行数を実測**した（`awk` による集計）。結果は以下のとおり:
>
> | セクション | 行数 |
> |-----------|------|
> | 設計・実装フロー（変更規模別） | 58 |
> | 作業完了時の報告フォーマット | 21 |
> | コーディングルール（全エージェント共通） | 20 |
> | プロジェクト概要 / ドキュメント構成 / DB スキーマ変更時 | 各 15 |
> | （以下 12 セクション） | 3〜12 |
>
> 上位3セクションで 99行（全体の 39%）を占め、うち「コーディングルール」20行は
> **`src/` を触らない作業では一度も使われない**。この 20行が、フローや報告フォーマットと同じ重みで
> 毎セッション読まれている状態だった。分割の対象として妥当と判断した。
>
> なお課題1には、事例に依存しない構造的な根拠もある: **`paths:` ルールは「該当ファイルを読んだときに必ずロードされる」という保証を持つ**。
> 常時ロードは「文脈に埋もれる可能性」を排除できないが、`paths:` は発火条件が機械的に決まる。この保証は効果測定を待たずに成立する。
>
> **ユーザー側で `/doctor` を実行すればトリム提案も得られる**ため、追加の削減余地はそちらで確認されたい。

### 方針

- **ルールは「いつ読まれるか」で置き場所を決める**。毎セッション必要なものだけ CLAUDE.md に残し、
  特定のファイルを触るときだけ必要なものは `.claude/rules/` に `paths:` 付きで置く
- **「Claude が忘れたら破綻する」ルールはフックに落とす**。CLAUDE.md は context であって強制力がない
- **バンドルスキルと競合しない命名にする**。Claude Code 本体が提供する機能を潰さない
- **派生プロジェクトへの影響を設計時点で織り込む**。リネームは破壊的変更なので、適用指示書とセットで出す
- **リスクの低いものから段階的に入れる**。「入れてから重ければ縮退」ではなく「軽く始めて必要なら足す」

### 非目的（本 Phase でやらないこと）

| 項目 | 送り先 | 理由 |
|------|--------|------|
| `context: fork` によるスキルのコンテキスト分離 | Phase 4 | 挙動変化が大きく、Phase 3 の変更と同時に入れると原因切り分けが困難 |
| TypeScript LSP プラグイン導入・`.mcp.json` バージョン固定 | Phase 4 | 外部依存の導入。テンプレート内部の構成刷新とは独立 |
| テンプレート一式のプラグイン化 | Phase 4 | Phase 3 で構成が固まってから着手すべき |
| `sandbox` 設定 | Phase 4 | WSL2 前提は既に整っているが、**Dev Container との併用時の挙動確認が別途必要**なため独立タスクとする |
| バンドルスキル（`/security-review` / `/simplify` / `/run` / `/verify`）のフロー組み込み | Phase 4 | Phase 3-B のリネームで名前空間を整理した後でないと、どのスキルが何を担うかの整理ができない |

## 3. 機能・画面設計（Stage 1）

本テンプレートは Web 画面を持たない。ユーザーが触れる「接点」は以下の3種であり、これを本設計書における「画面」と読み替える。

| 接点の種類 | 具体物 | 本 Phase での変更 |
|-----------|--------|------------------|
| 明示的に叩くもの | スラッシュコマンド | `/code-review` → `/review-impl` にリネーム |
| 勝手に発火するもの | フック | 4種を2段階に分けて新設 |
| 常に効いているもの | CLAUDE.md / `.claude/rules/` | 6ファイルへ分割し、発火条件を付ける |

### 3-1. 対象接点と操作フロー

#### (A) スラッシュコマンド

| コマンド | 変更 | 概要 |
|---------|------|------|
| `/review-impl` | **新規（改名）** | 従来の `/code-review`。設計書突き合わせ＋型安全性＋自動修正 |
| `/code-review` | **バンドルへ解放** | Claude Code 本体の差分レビュー |
| `/code-review ultra` | **利用可能化** | ブランチ全体のマルチエージェント・クラウドレビュー |

**操作フロー（M 規模の実装後）**:

1. 実装完了
2. `/review-impl` を実行 → 設計書との整合性・型安全性をレビュー、重要指摘は自動修正
3. （任意）大きな変更のときだけ `/code-review ultra` を実行し、ブランチ全体を多角的にレビュー
4. `/browser-test` → `/build-check` → `/update-docs` → コミット

> 3 は**フローに組み込まない**。課金を伴うユーザートリガー機能であり、Claude 側から起動できないため、
> CLAUDE.md には「必要に応じて手動で実行できる」と選択肢として記載するに留める。
> なお、リネームで回復するのは ultra だけではなく、**日常的に使えるバンドルの差分レビュー `/code-review` も含む**。

#### (B) フック（自動発火）

**先行導入（3-C1）— 誤爆リスクが低く、情報提示に徹するもの**

| フック | 発火タイミング | ユーザーから見た挙動 |
|-------|--------------|---------------------|
| SessionStart | セッション開始・再開時 | ブランチ名・未プッシュコミット数・進行中の機能設計書が自動で提示され、状況説明が不要になる |
| PreCompact | コンパクト実行前 | 進行中の設計書パス・規模判定結果が保持され、コンパクト後も文脈が残る |

**後続導入（3-C2）— 作業に介入するため、条件のチューニングが必要なもの**

| フック | 発火タイミング | ユーザーから見た挙動 |
|-------|--------------|---------------------|
| PostToolUse(Edit) | `src/**/*.{ts,tsx}` の編集直後 | **まず lint 自動修正のみで開始**。体感コストを確認したうえで、問題なければ型チェック（`--incremental`）を追加する |
| SubagentStop | サブエージェント終了時 | 変更ファイル数と `git diff` コマンドが提示され、差分確認の実行コストが下がる |

> **SubagentStop の位置づけ**: CLAUDE.md には既に「サブエージェントの結果は必ずメインで差分確認する」という文言ルールがある。
> 単に同じ内容を通知するだけでは既読スルーされるため、**変更ファイル数と実行可能な差分コマンドをその場に出す**ことで、
> 「読む」から「実行する」への距離を縮めることを狙いとする。数セッション運用して行動が変わらなければ**撤去する**。

**採用を見送ったフック**（レビュー §4.3 の候補のうち）:

| フック | 見送り理由 |
|-------|-----------|
| `Stop` | 未コミット変更の通知は SubagentStop と目的が重複する。3-C2 の効果を見てから判断する |
| `FileChanged`（schema.prisma） | `.claude/rules/prisma.md` の `paths:` で同じ目的を達成できる。二重に発火させる必要がない |
| `InstructionsLoaded` | 常設フックとしてではなく、**3-4 の検証時に一時的に有効化するデバッグ手段**として使う |

#### (C) 常時ロード文書

**`.claude/rules/` に移すもの**（特定ファイルを触るときだけ必要 ＝ `paths:` で発火条件を付ける）

| ファイル | paths | CLAUDE.md からの移設元 |
|---------|-------|----------------------|
| `typescript.md` | `src/**/*.{ts,tsx}` | コーディングルール § TypeScript |
| `react-nextjs.md` | `src/features/**/*.tsx`, `src/components/**`, `src/app/**/*.tsx` | コーディングルール § React/Next.js、§ UI 実装 |
| `api.md` | `src/app/api/**`, **`src/features/**/hooks/**`** | コーディングルール § API Route、API型契約の必須化 |
| `prisma.md` | `prisma/schema.prisma`, `tools/export-to-sql.ts`, `tools/scripts/generate-table-docs.ts` | **DB スキーマ変更時の必須ルール** |
| `tools-scripts.md` | `tools/**` | スクリプトの整理ルール |
| `docs.md` | `docs/features/**`, `docs/設計書/**` | 設計書の改訂履歴ルール、機能設計書の運用ルール |

> `api.md` の paths に `src/features/**/hooks/**` を含めるのは、**API 型契約が BE/FE 双方に効く必要があるため**。
> `src/app/api/**` のみだと、BE と FE を別サブエージェントに委譲した場合に FE 側が一度もルールを読まずに実装を終える。

**CLAUDE.md に残すもの**（毎セッション必要 ＝ パスに紐づかない）

| セクション | 残す理由 |
|-----------|---------|
| 対話は日本語 / Next.js 16 注意 | 全作業に効く。特定パスに紐づかない |
| サブエージェントのモデル指定 | エージェント起動時に必要。ファイル編集とは無関係 |
| プロジェクト概要 / Build & Dev Commands | 作業開始時に必要 |
| ドキュメント構成と役割分離 | **`.claude/rules/` の行を追加する**（タスク 3-A に含む） |
| 設計・実装フロー（変更規模別） | 全作業の入口 |
| 作業完了時の報告フォーマット | 全作業の出口 |
| **サブエージェント運用ルール** | 委譲品質の担保。ファイルパスに紐づかない |
| 設計書優先の原則 / バグ修正の原則 | 調査・修正の進め方。パスに紐づかない |
| **セキュリティの原則** | 最重要ルール。**分割で常時ロードから外してはならない** |
| push のタイミング / 作業の進め方 | 全作業に効く |
| **`.claude/rules/` の索引表**（新規） | どのルールがどの条件で読まれるかを一覧化し、分散による見通しの悪化を防ぐ |
| **DB 3点同期へのポインタ1行**（新規） | `paths:` ルールはコンパクト後に自動再注入されないため、意図的な例外として1行だけ残す |

**行数の見積もり**: 現状 252行 − 移設分 約74行 ＋ 索引表・ポインタ 約10行 ＝ **約188行**（目標の 200行以下を満たす）

### 3-3. 想定リスクと対策

| リスク | 影響 | 対策 |
|-------|------|------|
| `paths:` ルールはコンパクト後に自動再注入されない | 長時間セッションで DB ルールが失われる | CLAUDE.md に「DB スキーマ変更時は `.claude/rules/prisma.md` を必ず読む」という**1行のポインタ**を残す。PreCompact フック（3-C1）でも進行中の文脈を退避する |
| 分割時にルールが行き場を失い、消失する | 最重要ルール（セキュリティ等）が効かなくなる | 3-1(C) で**移設先と残置先を全セクション分明示**した。実装時は移設前後の差分で全セクションを突き合わせ、受け入れ条件で検証する |
| PostToolUse(Edit) が毎編集で走り、体感が重くなる | 実装のテンポが落ちる | **lint のみで開始**し、体感を確認してから型チェックを追加する。`if: "Edit(src/**/*.{ts,tsx})"` で対象を絞る |
| SubagentStop が既読スルーされる | フックを入れた意味がない | 情報提示ではなく実行可能なコマンド提示にする。数セッション運用して効果がなければ撤去する |
| `/code-review` リネームで既存の習慣・ドキュメントが壊れる | ユーザー・派生プロジェクトの混乱 | 7章の実測リストに沿って機械的に置換。適用指示書に移行手順を明記 |
| ルール分割で情報が散り、どこに何があるか分からなくなる | 保守性の低下 | CLAUDE.md に `.claude/rules/` の索引表を置く |
| 動的コンテキスト注入が Windows（Git Bash なし）で失敗する | スキルが起動しない | 3-E は着手前に実行環境を確認する。失敗する環境が想定されるなら `shell: powershell` 併記か、**本 Phase では見送る** |

### 3-4. 検証方法

受け入れ条件のうち「ルールが確実に効いているか」「フックが誤爆しないか」は、以下の手順で客観的に確認する。

#### (1) ルールのロード検証

`InstructionsLoaded` フックを**検証中だけ一時的に**有効化し、どのルールがいつ読まれたかをログ出力する。
または `claude --debug` でロードされた instruction ファイルを確認する。

| 操作 | 期待 |
|------|------|
| `prisma/schema.prisma` を Read | `prisma.md` がロードされる |
| `src/app/api/foo/route.ts` を Read | `api.md` がロードされる |
| `src/features/foo/hooks/useBar.ts` を Read | `api.md` がロードされる |
| `docs/guide/*.md` を Read | `typescript.md` / `api.md` / `prisma.md` のいずれもロードされない |

#### (2) フックの発火／非発火マトリクス

各フックについて「発火すべきケース」と「発火してはいけないケース」を最低2つずつ実行して確認する。

| フック | 発火すべき | 発火してはいけない |
|-------|-----------|------------------|
| PostToolUse(Edit) | `src/features/foo/Bar.tsx` の編集 / `src/lib/services/baz.ts` の編集 | `docs/設計書/API一覧.md` の編集 / `.claude/settings.json` の編集 |
| SessionStart | 新規セッション / `--resume` での再開 | セッション途中の `/clear` 以外の操作 |
| SubagentStop | `coding-specialist` の終了 | メインスレッドのツール実行終了 |
| PreCompact | 自動コンパクト / `/compact` | 通常のターン終了 |

### 4-5. フックの設計（タスク 3-C1 / 3-C2）

#### 4-5-1. settings.json への登録

```json
{
  "hooks": {
    "SessionStart": [
      { "matcher": "startup|resume|compact",
        "hooks": [{ "type": "command", "command": "node .claude/hooks/session-start-context.js", "timeout": 10 }] }
    ],
    "PreCompact": [
      { "hooks": [{ "type": "command", "command": "node .claude/hooks/pre-compact-save.js", "timeout": 10 }] }
    ],
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "if": "Edit(src/**/*.{ts,tsx})",
            "command": "node .claude/hooks/post-edit-lint.js", "timeout": 30,
            "statusMessage": "lint 自動修正中..." },
          { "type": "command", "if": "Write(src/**/*.{ts,tsx})",
            "command": "node .claude/hooks/post-edit-lint.js", "timeout": 30,
            "statusMessage": "lint 自動修正中..." }
        ] }
    ],
    "SubagentStop": [
      { "hooks": [{ "type": "command", "command": "node .claude/hooks/subagent-stop-diff.js", "timeout": 10 }] }
    ]
  }
}
```

> 既存の `PreToolUse` / `PostToolUse`（Bash matcher）はそのまま維持し、`PostToolUse` に
> `Edit|Write` matcher のエントリを追加する形になる。
>
> **`if` は `ToolName(pattern)` 形式で単一ツールにしかマッチしない**ため、`matcher: "Edit|Write"` に対して
> `if: "Edit(...)"` だけを書くと、**Write ツールで新規 `.tsx` を作成したときにフックが発火しない**。
> `Edit` 用と `Write` 用の2エントリに分けることで、受け入れ条件「`.ts`/`.tsx` を編集したとき lint が
> 自動修正される」を新規作成のケースでも満たす。

#### 4-5-2. 各スクリプトの入出力設計

| スクリプト | 読む入力 | 出力 | 失敗時 |
|-----------|---------|------|-------|
| `session-start-context.js` | `source`（startup/resume/compact） | `hookSpecificOutput.additionalContext` に状況サマリ | `exit 0`（何も注入しない） |
| `pre-compact-save.js` | `trigger`（manual/auto） | `.claude/.session-context.json` に退避＋`systemMessage` | `exit 0` |
| `post-edit-lint.js` | `tool_input.file_path` | 修正した場合 `systemMessage`、未解決エラーがあれば同じく `systemMessage` | `exit 0`（lint 未導入時はスキップ） |
| `subagent-stop-diff.js` | `agent_type` | `systemMessage` に変更ファイル数と差分コマンド | `exit 0` |

**共通方針**: 本 Phase のフックは **すべて非ブロッキング**とする。`decision: "block"` や `continue: false` は使わない。
既存の型チェックフック（`permissionDecision: "deny"`）とは役割が異なり、これらは「気づきを与える」のが目的であるため。

**`session-start-context.js` の出力例**:

```
[状況] branch: master / 未プッシュ: 3 commits
[進行中の設計書]
  - docs/features/20260812_ハーネス構成刷新_Phase3.md (🟡 実装中)
[未コミット変更] 5 ファイル
```

取得方法:
- ブランチ: `git rev-parse --abbrev-ref HEAD`
- 未プッシュ数: `git rev-list --count @{upstream}..HEAD`（upstream 未設定時はスキップ）
- 進行中の設計書: `docs/features/*.md`（`completed/` `pending/` `TEMPLATE.md` を除く）を列挙し、メタ情報の全体ステータス行を抽出
- 未コミット変更: `git status --porcelain` の行数

`source === "compact"` の場合は、`.claude/.session-context.json` があれば併せて注入し、読んだ後に削除する。

**`pre-compact-save.js` の退避内容**:

```json
{
  "savedAt": "<ISO8601>",
  "activeFeatureDocs": ["docs/features/20260812_....md"],
  "branch": "master",
  "uncommittedFiles": 5
}
```

> **PreCompact は `additionalContext` に非対応**（公式ドキュメントで確認済み。PreCompact の decision pattern は
> `decision: "block"` であり、コンテキスト注入の手段を持たない）。したがって
> **ファイル退避 → SessionStart(compact) で読み戻す**方式で確定とする。単純化の余地はない。

**`post-edit-lint.js` の挙動**:

1. `tool_input.file_path` を取得。`src/` 配下の `.ts` / `.tsx` でなければ `exit 0`
2. `node_modules/.bin/eslint` が無ければ `exit 0`（テンプレート利用開始直後の考慮）
3. `npx eslint --fix <file>` を実行
4. 修正が入った場合、または未解決のエラーが残った場合のみ `systemMessage` を出力。問題なしなら無出力

> **型チェックは初期実装に含めない**。Stage 1 レビュー（product-advisor #2）の指摘に従い、
> lint のみで数セッション運用して体感コストを確認したうえで、追加の可否を判断する。
> 追加する場合は `tsc --noEmit --incremental` でキャッシュを効かせる。

**`subagent-stop-diff.js` の挙動**:

1. `git status --porcelain` で変更ファイル数を取得
2. 0 件なら `exit 0`
3. `systemMessage` に「`{agent_type}` の終了後、{N} ファイルに変更があります。`git diff` で内容を確認してください」と出力

### CLAUDE.md の既存マーカーコメント

`CLAUDE.md:5,7` に `<!-- BEGIN:nextjs-agent-rules -->` / `<!-- END:nextjs-agent-rules -->` が存在する。
HTML コメントはコンテキスト注入前に除去されるため Claude からは見えず、トークンも消費しない。
Phase 1 で `AGENTS.md` への参照を削除した経緯から、**AGENTS.md との同期用に置かれた残骸である可能性が高い**。

**3-A ではこのマーカーに触らない**。用途が確定していないものを構成刷新のついでに消すと、
外部ツールが依存していた場合に切り分けが困難になる。Phase 4 で用途を確認したうえで削除可否を判断する。

### その他

- フックは「Claude が忘れても効く」のが利点だが、**誤爆すると全作業の邪魔になる**。`if` の条件は Stage 2 で1つずつ確定させ、3-4 の手順で発火/非発火を実際に確認する
- `.claude/rules/` に移した内容を CLAUDE.md 側に残したままにしない（**二重管理の禁止**）。ただし DB ルールのポインタ1行だけは意図的な例外とし、その旨をコメントで明記する
- Phase 3-D（checklist 移設）は他タスクと依存関係がないため、Phase 3 全体の承認を待たずに着手してよい
