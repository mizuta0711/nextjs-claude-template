## 作業 1: 全 SKILL.md のフロントマター検査（最重要）

`.claude/skills/*/SKILL.md`（および存在すれば `.claude/commands/*.md`）を**全件**開き、
以下の3点を検査して該当するものだけ修正する。テンプレート由来でない独自スキルも対象。

### 1-A. フロントマターの欠落

ファイル先頭が `---` で始まっていないスキルは、`description` が本文1段落目からの
フォールバックになり、Claude の起動判断が不安定になる。以下を先頭に追加する:

---
name: <ディレクトリ名と同じ>
description: <何をするスキルか。「いつ使うか」を先頭に書く>
---

テンプレート側では `.claude/skills/done/SKILL.md` がこれに該当した。修正後の姿:

---
name: done
description: 作業完了時に、決められたテーブル形式で完了報告を出力する。S/M/Lフローの最終ステップ。
---

注意: `done` に `disable-model-invocation: true` は**付けないこと**。
CLAUDE.md の S/M/L フローで Claude 自身が最終ステップとして実行するスキルであり、
これを付けると Claude から起動できなくなりフローが成立しない。

### 1-B. アンダースコア区切りのフロントマターキー

Claude Code のフロントマターは**ハイフン区切り**が正。
アンダースコア区切りのキーは不正キーとして無視される。

| 誤 | 正 |
|----|-----|
| `user_invocable` | `user-invocable` |
| `allowed_tools` | `allowed-tools` |
| `argument_hint` | `argument-hint` |
| `disable_model_invocation` | `disable-model-invocation` |

テンプレート側では `complete-feature/SKILL.md` に `user_invocable: true` があった。
ただし `user-invocable` の既定値は `true` なので、**書き直すのではなく行ごと削除**する。
そのうえで、ユーザーが明示的に呼ぶべき完了処理スキルであるため以下に置き換えた:

disable-model-invocation: true

このフィールドを付けてよいのは「**Claude が自律的に走らせると困るスキル**」に限る。
本プロジェクトでの判断基準:
- 付ける: 完了処理、リリース処理、破壊的操作を伴うもの
- 付けない: CLAUDE.md のフローで Claude が実行するステップになっているもの

### 1-C. SKILL.md 本文中の `$0` / `$1` / `$2`

これが最も実害が大きい。Claude Code は SKILL.md 本文の `$0` `$1` `$2` を
**スキル引数の置換プレースホルダ**（`$ARGUMENTS[0]` 等の短縮形）として展開する。
そのため、bash のつもりで書いた `$0` はコードブロック内であっても壊れる。

テンプレート側の `update-docs/SKILL.md` にあった実例:

git diff --name-only HEAD~${0:-1}

これは引数ありなら意図しない文字列に置換され、引数なしなら未置換のまま bash に渡り、
bash の `$0`（シェル名）が入って `HEAD~bash` になる。**どちらでも必ず失敗する。**

修正方針は、フロントマターで名前付き引数を宣言し、本文では `$名前` を使う:

（フロントマター）
argument-hint: "[遡るコミット数（省略時は1）]"
arguments: [depth]

（本文）
`$depth` に数値が入っていればその値を、空文字なら `1` を使って以下を実行する:

git diff --name-only HEAD~1

全スキルを `grep -rn '\$[0-9]' .claude/skills/` で走査し、
bash 変数のつもりで書かれている箇所をすべて洗い出すこと。

## 作業 1: permissions を .claude/settings.json（コミット対象）へ

まず現状を確認する:

- `.claude/settings.json` に `permissions` があるか
- `.claude/settings.local.json`（gitignore 対象）にしか無いなら、それが問題。
  複製・クローンした先に権限設定が一切引き継がれない状態になっている

チームで共有すべきルールを `.claude/settings.json` に移す。
`settings.local.json` にはそのマシン固有の緩和だけを残す。

### allow に入れるもの

**本プロジェクトの `package.json` の scripts を実際に読み**、開発で常用する
読み取り専用・冪等なコマンドだけを列挙する。テンプレートの内容を丸写ししない。
（例: `npm run build` が無いプロジェクトにその行を書かない）

目安: `Read` / `Glob` / `Grep`、`git status|diff|log|show|branch|add`、
ビルド・lint・型チェック、`prisma generate|validate`、プロジェクト固有の生成スクリプト。

### ask に入れるもの

取り返しはつくが影響が大きいもの: `git reset`、`git checkout`、
`prisma migrate`、`prisma db push`。

判断のポイント2つ:

- `git reset` を **deny にしないこと**。CLAUDE.md の「バグ修正の原則」で
  「複数の仮説修正が失敗した場合は git reset でまとめて戻す」を推奨しており、
  deny にすると自分のルールと矛盾する。ask が正解。
- `git push` は **ask ではなく allow** に置く。push のタイミングは CLAUDE.md の
  「push のタイミング」で行動ルールとして既に縛られており、権限レイヤーで
  毎回確認を挟むのは冗長。危険なのは強制 push なので、そちらを deny で止める。
  （テンプレート側では当初 ask に置いたが、実運用の邪魔になるため allow へ変更した）

### deny に入れるもの

- `.env` 系の読み取り。ただし **`Read(./.env*)` の一括 deny は避ける**
  （`.env.example` まで読めなくなり、必要な環境変数の把握ができなくなる）。
  Next.js の命名規則に沿って個別に指定する:
  `Read(./.env)` `Read(./.env.local)` `Read(./.env.development*)`
  `Read(./.env.production*)` `Read(./.env.test*)`
- `Read(./secrets/**)` 等、プロジェクトに機密ディレクトリがあれば追加
- `Bash(rm -rf *)`
- `Bash(git push --force*)` `Bash(git push -f *)`
- `Bash(npx prisma migrate reset*)`

deny はどの設定レイヤーの allow よりも優先されるため、settings.local.json に
広い allow が残っていても deny は効く。

## 作業 3: フックに if 条件を付与

`.claude/settings.json` の hooks で、各 hook エントリに `if` を追加する。
`if` はパーミッションルール構文の公式フィールドで、
PreToolUse / PostToolUse / PostToolUseFailure / PermissionRequest / PermissionDenied で評価される。

これが無いと、Claude が `ls` を1回叩くだけでフックスクリプトが全数起動する。

  { "type": "command", "if": "Bash(git commit:*)",
    "command": "node .claude/hooks/pre-commit-type-check.js", "timeout": 120 }

`if` の値は、そのフックスクリプトが内部で判定しているコマンドと一致させること
（スクリプト内の正規表現を読んで確認する）。スクリプト側の判定は
二重防御として残す。timeout は**秒単位**。

## 作業 4: フックのブロック方式を見直す

フックスクリプトが `continue: false` + `stopReason` を返している箇所を洗い出す。
`continue: false` は **Claude を完全に停止させる**フィールドで、
「Claude に直してほしいだけ」の事象には強すぎる。

Claude に自己修復させたいもの（型エラー、lint エラー等）は以下に変更する:

  console.log(JSON.stringify({
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "型チェックに失敗しました。修正してから再度コミットしてください:\n" + out
    }
  }));

一方、**人間の判断を必ず挟みたいもの**（DB バックアップ失敗、本番系への操作）は
`continue: false` のままにする。テンプレート側ではこの非対称を意図的に残し、
両方のスクリプトのコメントに理由を書いた。同じ判断を本プロジェクトでも行い、
どちらにしたかをコメントに残すこと。

## 作業 5: スキルに allowed-tools を付与

また、特定 MCP しか使わないエージェントには以下を付けると、

## 作業 1: CLAUDE.md を .claude/rules/ へ分割

### 手順

1. まず現状を測る。`wc -l CLAUDE.md` と `grep -n '^## ' CLAUDE.md` でセクション別の行数を出す。
   200行を大きく超えていないなら、この作業は**やらなくてよい**（分割自体が目的ではない）。
2. 各セクションについて「**特定のパスのファイルを触るときだけ必要か**」を判定する。
   - パスに紐づく → `.claude/rules/<名前>.md` に移し、フロントマターに `paths:` を書く
   - パスに紐づかない → CLAUDE.md に残す
3. 移設したら CLAUDE.md 側から**必ず削除する**（二重管理の禁止）。

### 判定を誤りやすい箇所（テンプレート側で実際に指摘を受けた）

Stage 1 レビューで、以下4カテゴリが「どのルールファイルにも行き場がないまま
CLAUDE.md からも消える」寸前だった。**必ず残置側に分類すること**:

| セクション | 分類 | 理由 |
|-----------|------|------|
| セキュリティの原則 | **CLAUDE.md に残す** | 最重要ルール。特定パスに紐づかない |
| サブエージェント運用ルール | **CLAUDE.md に残す** | 委譲品質の担保。ファイル編集と無関係 |
| 設計書の改訂履歴・機能設計書の運用 | `rules/docs.md` へ | `docs/features/**`, `docs/設計書/**` に紐づく |
| Next.js のバージョン注意 | **CLAUDE.md に残す** | コード執筆全般に効く |

移設前後で全セクションを突き合わせ、**どこにも行かなかったセクションがゼロ**であることを確認する。

### paths の設計で注意する点

- API 型契約のように **BE と FE の両方で効く必要があるルール**は、
  `src/app/api/**` だけでなく `src/features/**/hooks/**` や `src/lib/services/**` も含める。
  片側だけだと、別サブエージェントに委譲したときに一方がルールを読まずに実装を終える
- 本プロジェクトのディレクトリ構成を実際に確認してから paths を書く。
  テンプレートと構成が違えば paths も変わる

### CLAUDE.md に追加するもの

- `.claude/rules/` の索引表（どのルールがどの条件で読まれるか）
- 「ドキュメント構成と役割分離」表に `.claude/rules/` の行
- **paths ルールはコンパクト後に自動再注入されない**ため、DB スキーマ変更のような
  「忘れると壊れる」ルールだけは要約1行を CLAUDE.md 側に残す（意図的な例外である旨を
  HTML コメントで明記する。HTML コメントはコンテキストに載らないのでトークンを消費しない）

## 作業 2: スラッシュコマンドの名前衝突を解消

本プロジェクトの `.claude/skills/` に、Claude Code のバンドルスキルと同名のものがないか確認する。
`/help` の一覧やドキュメントで、バンドル側に同名コマンドが存在するかを調べること。

テンプレートでは `/code-review` が衝突しており、リネーム（`/review-impl`）で解消した。
これにより標準の差分レビューと `/code-review ultra`（マルチエージェント・クラウドレビュー）が使えるようになる。

### 手順と落とし穴

1. `grep -o '/旧名' <file> | wc -l` で**出現数を実測**する。
   `grep -rn` の行数で数えると、同一行に複数出現する分を取りこぼす（テンプレートでは
   32 と数えていたが実際は 33 だった）
2. `git mv` でスキルディレクトリを改名し、SKILL.md の `name:` を変更する
3. **SKILL.md 本文に旧名を含む出力ファイル名などが無いか確認する。**
   テンプレートでは `docs/reviews/YYYYMMDD_HHMMSS_code-review.md` という記述があり、
   検証 grep が `docs/reviews/` を除外していたため**漏れても検出できない位置**にあった
4. ファイル名自体に旧コマンド名を含む図・ドキュメントも改名する
5. CLAUDE.md・README・フロー定義・ガイド・図の参照をすべて置換する
6. `docs/reviews/` と `docs/features/completed/` は過去の記録なので**遡及編集しない**

## 作業 3: フックの追加

一度に4種入れず、**2段階に分ける**。

### 先行（誤爆リスクが低い）

- `SessionStart`: ブランチ・未プッシュ数・未コミット数・進行中の設計書を additionalContext に注入
- `PreCompact`: 進行中の文脈をファイルに退避し、`SessionStart(source=compact)` で読み戻す
  ※ **PreCompact は additionalContext に非対応**。ファイル経由でしか受け渡せない

### 後続（作業に介入するため、先行分を数セッション運用してから）

- `PostToolUse(Edit|Write)`: 編集直後の lint 自動修正
- `SubagentStop`: 変更ファイル数と差分コマンドの提示

### 実装上の必須事項

- **`if` は `ToolName(pattern)` 形式で単一ツールにしかマッチしない。**
  `matcher: "Edit|Write"` に対して `if: "Edit(...)"` だけを書くと、
  **Write での新規ファイル作成を取りこぼす**。Edit 用と Write 用の2エントリに分けること
- 本 Phase のフックは**すべて非ブロッキング**にする。`continue: false` や
  `decision: "block"` は使わない（既存の型チェックフックとは役割が違う）
- **型チェックを PostToolUse に入れない。** まず lint だけで運用して体感コストを
  確認してから追加を判断する。「入れてから重ければ縮退」ではなく「軽く始めて必要なら足す」
- 退避ファイル（`.claude/.session-context.json` 等）は `.gitignore` に追加する
- 出力するパスはスラッシュ区切りに正規化する（Windows で表記が揃わない）

## 作業 4: スキルの動的コンテキスト注入

「`git diff` を実行せよ」という指示を、スキル読み込み時点で結果を埋め込む形に変える。

- 1行なら `` !`git diff --name-only` ``
- 複数行のスクリプトなら ```! ブロック

**着手前提**: `bash` が使えること。ネイティブ Windows で Git Bash が無い環境では
フロントマターに `shell: powershell` が必要になり、コマンド自体の書き換えも要る。
その場合は**この作業を見送ってよい**。

注入されたコマンドの分だけ `allowed-tools` を広げること
（テンプレートでは `git diff-tree` / `grep` の追加が必要だった）。

## 作業 5: statusLine

設定1行に近いコストで、モデル・ブランチ・コンテキスト使用率・未コミット数が常時見える。
`jq` ではなく Node で書くと Windows でも動く。

`statusLine` の入力 JSON には**ブランチ名が含まれない**（worktree セッション時の
`worktree.branch` を除く）。ブランチを出すならスクリプト内で `git branch --show-current` を叩く。
`context_window.used_percentage` はセッション初期と `/compact` 直後は `null` になりうるので、
値の有無を必ず確認してから表示すること。

## 実装して初めて分かったこと（テンプレート側の実績）

設計段階では見えず、**手を動かして初めて判明した**もの。同じ手順を踏むなら先に知っておくとよい。

### 1. 200行の目標は「コメント除去後」で測る

ブロックレベルの HTML コメントは**コンテキスト注入前に除去される**ため、行数の目標に対しては
実質カウントされない。テンプレートでは raw 199行 / コメント除去後 190行だった。
`wc -l` の数字だけを見て過剰に削らないこと。逆に、メンテナ向けのメモは
HTML コメントで書けばトークンを消費せずに残せる。

### 2. 用途不明のマーカーコメントは触らない

テンプレートの CLAUDE.md には `<!-- BEGIN:nextjs-agent-rules -->` /
`<!-- END:nextjs-agent-rules -->` という既存マーカーがあった。AGENTS.md 同期用の残骸と
推測されたが、**用途が確定していないものを構成刷新のついでに消さない**方針を採った。
外部ツールが依存していた場合、切り分けが困難になるため。

### 3. 設計書を `completed/` に移すと相対リンクが壊れる

機能設計書を `docs/features/` から `docs/features/completed/` へ移動すると、
その設計書内の `../reviews/` `../../.claude/` などが 1 階層ずれる。
同時に、**その設計書を参照している側**（レビュー文書・適用指示書）のパスも追従が要る。
移動後に必ずリンク切れを検査すること。

### 4. `.doc-sync.md` の記録には鶏と卵がある

「未プッシュの全コミットを記録する」ルールに対し、**記録を書いたコミット自身が未記録になる**。
既存の例外規定は「`.doc-sync.md` 自体の更新のみのコミットは記録不要」だが、
実運用では「記録＋他の変更」が同一コミットになることが多く、例外が効かない。
テンプレート側では `.doc-sync.md` だけを更新する追加コミットを3回打つ羽目になった。

**本プロジェクトに同じルールがあるなら、`/pre-push-check` 側で「最新コミットは対象外」と
するなどの見直しを併せて検討すること。**

### 5. 設計書のステータス更新は忘れやすい

テンプレートでは、実装に着手済みなのに機能設計書の全体ステータスが 🔵 設計中 のままだった。
**SessionStart フックの動作確認中に、フック自身がこれを検出した。**
フックで進行中の設計書とステータスを表示させる副次効果として、この種の更新漏れに気づける。

### 6. lint 未導入の環境では発火／非発火を出力で判別できない

`post-edit-lint.js` は eslint が無ければ黙ってスキップするため、
「対象外でスキップ」と「eslint 未導入でスキップ」が**どちらも無出力**になり区別できない。
パス判定ロジックは**単体テストで検証**すること（テンプレートでは発火3ケース・非発火5ケースを
別スクリプトで確認した）。
